Changelog

SealKeeper follows Semantic Versioning. Notable changes between releases are documented here, with security-relevant items tagged explicitly.

Summary. This page highlights what matters to operators. The complete, commit-level record is the CHANGELOG in the repository.
0.1.1 2026-10-27 security release

Upgrade from 0.1.0, after checking how your SK_MASTER_SECRET was produced (see the upgrade note below). Release page: v0.1.1 on GitHub.

Security

  • Hand-made master secrets are refused in production (medium). 0.1.0 refused only placeholders and short values, so a degenerate key (zeros, a counter, an encoded phrase) or a passphrase of words was accepted, and every secret sealed or derived from it was as guessable as the passphrase. Production now refuses at startup any value that was not drawn at random (GHSA-f24m-cpmv-84h2).

Upgrade note

  • A secret printed by openssl rand -base64 32 or another random generator keeps working. A hand-made one stops the server at startup, before the database is opened, so going back to 0.1.0 is safe. Moving to a new secret loses what was sealed with the old one (admin TOTP, SMTP and integration credentials, audit verification): follow the upgrade note in CHANGELOG.md before switching.
0.1.0 2026-10-27 first public release

First public release. Nothing was released before this version, so every security issue listed below affects earlier commits only and none affects a published release. Release page: v0.1.0 on GitHub.

Security

  • Two external reports, both medium: the admin TOTP lockout counter was cleared before the second factor was checked, so the TOTP code could be brute-forced (GHSA-xr59-fxvh-vx8h); the reveal page replaced the configured generation policy with a hard-coded one and misreported strength (GHSA-h3vw-xg58-625j).
  • Internal security audits (three rounds) fixed, among others: a silent downgrade to the weak built-in sample library; admin CSRF tokens not bound to the session; lockout bypass under concurrency; stolen sessions surviving credential changes; a placeholder SK_MASTER_SECRET accepted in production; an SMTP STARTTLS downgrade; default deployments pointing at an image namespace the project does not own (critical); and release tags pushed before the release gates ran.
  • Reveal tokens are no longer logged, audited or stored in clear: they are consumed by POST /api/v1/policy, referenced by a pseudonymous tokenRef, and kept only as a SHA-256 digest.
  • The audit log is now an HMAC-SHA256 chain keyed from SK_MASTER_SECRET, with a sealed head anchor that detects tail truncation.
  • Nonce-based Content-Security-Policy and security headers on every response; single-use TOTP codes; WebAuthn requires user verification; SIEM sinks cannot reach loopback, link-local or metadata addresses.

Added

  • Retention purge (RGPD): serve deletes ended sessions, old request tokens, captured mail, long-disabled admins and expired audit rows at boot and then daily, keeping the audit chain verifiable. Periods are set with SK_RETENTION_*.
  • sealkeeper admin enable --email <e> to recover from a state with no active admin.
  • Configuration knobs SK_MAIL_LANGUAGE and SK_INTEGRATIONS_ALLOW_PRIVATE; new audit events and metrics for recovery codes, step-up failures, dropped SIEM events and refused reveal-link openings.
  • Standalone release binaries embed the JS generation bundle.
  • docs/security/mail-authentication.md (sender identity, SPF, DKIM, DMARC) and an RFC 9116 security.txt on this site.

Changed

  • POST /api/v1/request requires application/json and same-origin requests; token consumption moves to POST /api/v1/policy. E-mailed /reveal/<token> links are unchanged.
  • Policies: G1/G2 need an inline library, and saving requires the guaranteed entropy to meet the level's floor (B1 ≥ 50, B2 ≥ 80, B3 ≥ 100 bits). Entropy credits only what the generators draw.
  • Admin step-up: changing e-mail, password or security keys, and managing other admins, requires the current password. Operator passwords must reach an estimated 100 bits of guessing entropy.
  • In production, an empty domain allowlist refuses every request (fail closed).
  • Mail templates are checked against an element/attribute allowlist; mail language is the instance setting SK_MAIL_LANGUAGE, no longer the requester's browser language.
  • Stricter configuration parsing: malformed values and unknown YAML keys are startup errors; SK_MODE=demo is refused in favour of SK_DEMO_MODE=true.
  • Release: tag push is the only trigger; the image is pushed by digest, every gate runs on that digest, and tags are added last.

Fixed

  • The Postgres backend now works (placeholders, booleans, audit chain timestamps, the audit page query).
  • SQLite enforces foreign keys; WebAuthn logins after the first no longer fail on SQLite.
  • The signed release image now ships the JS generation bundle.
  • The default Compose stack starts (library directory and /data ownership, Caddy healthcheck).
  • Every mail now carries its own random Message-ID.

Upgrade notes

  • Pin SK_MASTER_SECRET to a random 32-byte base64 value, identical across restarts and rebuilds. If the shipped placeholder was ever used, rotate the SMTP relay password and re-enrol every operator's TOTP.
  • Every admin session is invalidated: sign in again.
  • Reveal links issued before the upgrade stop working.
  • Set SK_TRUSTED_PROXY_CIDRS to the exact address of your reverse proxy.
  • List at least one domain before going live in production.
  • Open each existing policy in the editor; ask users who received passwords from a weak or ignored policy to rotate them.
  • Review custom mail templates, and set SK_MAIL_LANGUAGE=fr for French deployments.
  • API clients send Content-Type: application/json and consume tokens with POST /api/v1/policy.
  • Point images at ghcr.io/sched75-org/sealkeeper and cosign verification at the SCHED75-ORG/SealKeeper workflow identity.
  • Purge proxy, ingress and SIEM logs that contain reveal tokens.

The complete, numbered upgrade procedure is in the CHANGELOG.

Versioning policy

  • Patch releases (0.x.y) contain only bug fixes and security patches. Always backwards-compatible. Drop-in upgrade.
  • Minor releases (0.x.0) may add new admin settings, new API endpoints, or new generation policies. Backwards-compatible at the configuration level but may require reviewing the changelog before upgrading.
  • Major releases (x.0.0) may introduce breaking changes. Migration steps are documented per release.

Before reaching 1.0.0, breaking changes may also appear in minor releases. The codebase is too young to commit to API stability — that commitment arrives with 1.0.0 itself.
