Cryptographic Notes

The cryptographic primitives, the key lifecycle, and the architectural decisions that determine SealKeeper's security properties. This page is written for security reviewers, auditors, and contributors familiar with modern symmetric cryptography.

No custom cryptography. SealKeeper composes well-understood primitives from the Go standard library, golang.org/x/crypto and the browser's WebCrypto API. There is no custom cipher, no hand-rolled MAC, no novel KDF. The design work is in what the server is not given: it never sees a generated password.

2 · The reveal flow

Three consequences follow. The database holds no password, no ciphertext of a password and no key that could produce one. The link in the email is a single-use capability to fetch a policy, not a secret envelope. And SealKeeper is not zero-knowledge: the server serves both the policy and the JavaScript bundle that performs the generation, so whoever controls the server controls what the browser runs (see known limitations).

3 · Password generation in the browser

The generation bundle (sealkeeper-generation.umd.js) has a single module that touches randomness. Every draw goes through crypto.getRandomValues(); a uniform index in [0, max) is obtained by masking a 32-bit draw to the next power of two and rejecting values that land at or above max, which removes modulo bias. 

// web/src/crypto.js — cryptoRandomInt(max), abridged
let mask = max - 1;
mask |= mask >>> 1;  mask |= mask >>> 2;  mask |= mask >>> 4;
mask |= mask >>> 8;  mask |= mask >>> 16; mask >>>= 0;
const buf = new Uint32Array(1);
for (;;) {
  crypto.getRandomValues(buf);
  const candidate = (buf[0] & mask) >>> 0;
  if (candidate < max) return candidate;   // acceptance ≥ 50 %
}

Three generators consume these draws, selected by the policy the operator assigned:

GeneratorWhat it drawsTarget level
G1 · quotationsOne citation from the operator's corpus, admin-chosen transforms, groups of random digits, one separatorB1 (≥ 50 bits)
G2 · wordsIndependent draws from the operator's dictionary, one separator, one group of random digitsB2 (≥ 80 bits)
G3 · charactersRandom characters from a–z A–Z 0–9 (62), or 57 with ambiguous characters excluded, grouped in blocksB3 (≥ 100 bits)

Entropy is computed under Kerckhoffs' assumption — the attacker knows the policy, the corpus and the dictionary, everything except the draw — and credits only what is actually drawn: distinct library entries, the separator really emitted, the alphabet really used. Deterministic transforms earn nothing; for G1 the figure is a conservative lower bound. The generators and the calculator share one validated reading of the policy parameters, so a size claim that does not match the real draw is rejected rather than credited. The same calculateEntropy function drives the badge on the reveal page and the live preview in the admin policy editor, and the server mirrors its rules before it will serve a policy.

The ANSSI levels are fixed thresholds: B1 ≥ 50 bits, B2 ≥ 80 bits, B3 ≥ 100 bits. As a worked example, the default G3 draw of 20 characters from the 62-character alphabet yields 20 × log2 62 ≈ 119 bits (≈ 116.7 bits with the 57-character alphabet), which clears B3.

4 · Reveal tokens

A token is 32 bytes from crypto/rand, encoded as base64url without padding. The emailed link carries it as a path segment: 

https://<instance>/reveal/<43-character token>
PropertyImplementation
At restOnly token_hash = hex(SHA-256("sealkeeper-reveal-token:" + token)) is stored in request_tokens (SQLite or PostgreSQL). A database dump or backup yields no usable link. No key is involved: 256 bits of CSPRNG output cannot be recovered from a digest, and keeping the master secret out of the lookup means rotating it cannot orphan pending links.
Lifetime15 minutes from issue for an unconsumed link.
Opening the linkGET /reveal/<token> only previews the token's state; it does not consume it. The page is sent with Cache-Control: no-store and Referrer-Policy: no-referrer.
ConsumptionPOST /api/v1/policy with {"token":"…"} in a JSON body, same-origin only. In one transaction: UPDATE request_tokens SET consumed_at = ? … WHERE token_hash = ? AND consumed_at IS NULL; zero rows affected means another request won the race.
Second use410 Gone (token_consumed); an expired link is also 410 (token_expired).
Token in a query stringGET /api/v1/policy?token=… is refused with 400 token_in_query and never consumed, because URLs end up in proxy and SIEM access logs.
Policy firstThe policy is resolved and validated before the token is burned; if it cannot be served the answer is 503 policy_unavailable and the link still works.
GuessingToken lookups (the reveal page and the consuming POST) share a cap of 60 per client IP per 15 minutes, answered with 429.
AuditThe audit log and SIEM feeds carry a tok: reference (a truncated, domain-separated SHA-256 of the token), never the token itself.

5 · Keys and where they come from

Every long-lived key is derived from one operator-supplied value, SK_MASTER_SECRET: 32 random bytes, base64-encoded (openssl rand -base64 32). In production mode it is mandatory and placeholder or short values are refused at startup; in eval mode one is generated if missing.

Operator secrets at rest

internal/cryptobox wraps a small set of operator secrets with AES-256-GCM. Each seal draws a fresh 96-bit nonce and stores nonce ‖ ciphertext ‖ tag. Each field binds its own associated data, so a ciphertext copied into another column or another row refuses to decrypt:

FieldAAD
Admin TOTP secret and recovery codesSHA-256("sealkeeper-admin:<id>")
Setup-wizard draft (secret and codes)SHA-256("sealkeeper-admin-setup:<id>:<session>")
SMTP relay passwordSHA-256("sealkeeper-smtp")
Integration (SIEM sink) credentialsSHA-256("sealkeeper-integration:<id>")

Nothing the public flow produces passes through cryptobox: there is no generated password to encrypt.

6 · Operator authentication

  • Passwords. Hashed with bcrypt at bcrypt.DefaultCost. bcrypt reads only the first 72 bytes of its input; the strength estimate credits nothing beyond them.
  • Strength. An operator password needs at least 16 characters, three of the four character classes and at least 100 bits of estimated guessing entropy (the B3 floor). The estimator charges dictionary words (with case and leetspeak variants), product, instance and email words, years, sequences, keyboard walks and repetitions at what they cost an attacker who knows the pattern.
  • TOTP. RFC 6238 with HMAC-SHA-1, 6 digits, 30-second step, a 160-bit secret and one step of tolerated clock drift either way. The last accepted step is recorded per admin, so a code cannot be replayed within its window. Eight recovery codes of 50 bits each are issued at setup.
  • WebAuthn / FIDO2. Operators may enrol security keys and complete login with an assertion instead of the TOTP code. A signature-counter regression is treated as a cloned authenticator and refused.

7 · Audit log integrity

Each row of audit_log is chained to the previous one under the audit chain key: 

entry_hash   = hex(HMAC-SHA-256(audit_chain_key, prev_hash || canonical_v2))
canonical_v2 = JSON ["sealkeeper-audit-entry-v2", sequence_no, occurred_at,
                     event_type, actor, target, details_json]
  • Head anchor. A per-row chain cannot show that its newest rows were removed. The single-row table audit_head pins the newest sequence number and hash under its own MAC (a distinct domain tag), advanced in the same transaction as each append, so tail truncation is detected.
  • Retention. The daily purge deletes whole rows from the old end only (365 days by default, never below 180). The last deleted row is recorded as base_seq / base_hash, bound by the anchor MAC, so the oldest survivor still chains. Rows are never rewritten in place, and the purge refuses to run on a chain that does not verify.
  • Legacy rows. Rows written before the keyed chain existed (at or below audit_head.legacy_until) verify as plain SHA-256 v1; every later row must verify as v2.
  • Verification. /admin/audit re-verifies the chain on every page load and shows a chain integrity break warning when it fails — or when verification cannot run at all.
Residual risk. The scheme is symmetric. An attacker with write access to the database who saved an earlier, still MAC-valid copy of audit_head can cut the tail and write the copy back; the server catches this only while a process that saw the newer head is still running. Forwarding events to a SIEM gives an independent record of the real sequence.

8 · Pseudonymisation

Client IP addresses and User-Agent strings never enter the audit log in clear. They are replaced by the first 64 bits of an HMAC-SHA-256 keyed with the pseudonym key. An unkeyed hash would not do: the whole IPv4 space can be hashed in minutes, so a plain digest of an address is still personal data.

9 · Release integrity

  • Container image ghcr.io/sched75-org/sealkeeper: signed with cosign keyless (Sigstore, Rekor transparency log), with an SLSA build-provenance attestation and a CycloneDX 1.5 SBOM attested to it.
  • Standalone binaries: CycloneDX 1.5 SBOMs and a SHA256SUMS file with a detached GPG signature by the maintainer key BB1F EC0B 3D83 B6F0 3CCF 2869 FA3F BAF2 05E4 48DA.
  • The JavaScript bundle is built from source inside the image build and copied into the image, and embedded into the standalone binaries; it is therefore covered by the image signature and the checksums. It has no separate signature and the reveal page does not use Subresource Integrity.

Verification steps are in docs/security/verification.md.

10 · Known limitations

  • A compromised server can weaken generation. The server serves both the policy and the bundle. Whoever controls it, or the path between it and the browser, can serve a weaker policy or a modified bundle that produces predictable output. There is no SRI and no out-of-band check of the bundle a browser actually ran. See the threat model.
  • The link travels by email. Anyone who reads the message before the recipient — a compromised mailbox, a relay, a link-scanning gateway that executes pages — can consume the token first. Opening the link does not consume it, the link expires after 15 minutes, and a consumed link answers 410, so a theft shows up as a failed reveal for the legitimate user.
  • Rotating SK_MASTER_SECRET is destructive. Wrapped TOTP secrets, recovery codes, the SMTP password and integration credentials become unreadable, and the existing audit chain no longer verifies under the new key. Pin the value across rebuilds and back it up with the database.
  • bcrypt's 72-byte limit. Anything past 72 bytes of an operator password is ignored; strength scoring accounts for it, but the truncation is silent.
  • No independent rebuild check. Builds use -trimpath and pinned linker flags, and provenance is attested, but no independent reproduce-and-compare result is published.
  • No formal verification. The code has not been mechanically verified. We rely on standard-library primitives, the test suites and external review.
  • No independent third-party audit yet. The code is open for audit but has not undergone a commissioned review.
